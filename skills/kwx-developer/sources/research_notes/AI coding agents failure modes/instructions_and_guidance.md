# Instructing coding agents: vendor guidance and evidence on instruction files and skills

Research date: 2026-10-30. All vendor pages were fetched live on this date unless noted. Model names in the vendor docs (Claude Opus 5.5, GPT-6 Luna, and so on) are as the pages state them today.

## 1. What Anthropic recommends (Claude Code best practices, CLAUDE.md, Agent Skills, engineering posts)

### Takeaway
Anthropic's current position (Claude Code docs, fetched 2026-10-30) is: write down only what the agent cannot find by reading the repo, keep CLAUDE.md short (under 200 lines), give the agent a pass/fail check to run, and move any rule that must have zero exceptions out of prose and into hooks, deny rules or settings. Emphasis words (IMPORTANT, ALL CAPS) are now explicitly discouraged because current models over-apply them; if a line keeps being missed, the file is too long or the rule belongs in a hook.

### Cited Findings

Framing: deterministic vs non-deterministic instructions
- Claude Code splits every instruction into two kinds. Non-deterministic: "your prompt, CLAUDE.md, or a skill. The model then decides what to do with this information... there's no guarantee that it'll follow your instructions." Deterministic: "a hook, a deny rule, or a managed setting. Claude Code applies this every time, no matter what the model decided to do." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- "If you keep adding emphasis to a CLAUDE.md line and Claude still misses it, that's a sign the line belongs in a hook. The reverse holds too: if you have hooks for things that are only preferences, delete them and let Claude decide." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- "If something has to happen every time, make it a hook, a deny rule, or a managed setting. CLAUDE.md is for guidelines, and Claude is allowed to decide a guideline doesn't apply." Rules like "Never read .env", "Always run the formatter after editing", "Don't touch the migrations folder" are followed "almost every time"; for those where almost is not enough, move them to harness config. [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- A hook is for a rule with zero exceptions; "Prefer named exports has plenty, so that one stays in CLAUDE.md." Keep the enforced set small: "If you ever find yourself at forty of them, most are probably preferences that Claude could have weighed on its own." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- The docs argue that most of the time you want the model to decide: "Almost every guideline has exceptions, and current models are good at reading the code in front of them and judging whether a guideline fits the situation." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)

What goes into CLAUDE.md
- "Only write down what Claude can't find by reading the repo, or what it would otherwise spend time rediscovering every session." Test: "1. Could it find this by reading the code? 2. Would it actually go and look? If both are yes, leave it out." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Recommended contents: exact test, typecheck and lint commands (and how to run a single test file); "Places where the code is misleading: an old pattern that's everywhere but that new code must not copy, or a directory that looks unused but isn't"; decisions not in the repo ("which error helper the team settled on, how deploys work"); and "Anything you've had to correct twice already." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- "Every line in it takes a little of Claude's attention on every task, whether it's relevant or not." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- "If your repo already has one of these [a check], the single most useful line in your CLAUDE.md is the command that runs it." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Size: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Imports "help you organize a long file but don't reduce its context cost." [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Specificity: write instructions "concrete enough to verify": "Use 2-space indentation" instead of "Format code properly"; "Run npm test before committing" instead of "Test your changes"; "API handlers live in src/api/handlers/" instead of "Keep files organized". [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Structure: "group related instructions under markdown headers and bullets. Organized sections are easier for Claude to follow than dense paragraphs." [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Consistency: "if two instructions contradict each other, Claude may pick one arbitrarily." A built-in `/doctor prompt-audit` flags instructions written for older models, references to missing files, and contradictions. [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- "The more specific and concise your instructions, the more consistently Claude follows them." [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Delivery mechanism: "CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself... there's no guarantee of strict compliance, especially for vague or conflicting instructions." [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Compaction: "Project-root CLAUDE.md survives compaction: after /compact, Claude re-reads it from disk and re-injects it." Instructions given only in conversation can disappear after compaction; "Add conversation-only instructions to CLAUDE.md to make them persist." [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Path-scoped rules: `.claude/rules/*.md` with a `paths:` glob load only when Claude works on matching files (example: "Validate request bodies with the zod schemas in src/api/schemas/, don't hand-roll checks"). [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Claude Code reads AGENTS.md by default when no CLAUDE.md exists (requires v2.1.277+); a CLAUDE.md can import AGENTS.md to share one file across tools. [Claude Code memory docs](https://code.claude.com/docs/en/memory)

"What you can stop doing" (advice retired for current models)
- "Add IMPORTANT or ALL CAPS to instructions Claude keeps missing": retired. "Current ones follow a plainly worded line, and piling on emphasis mostly makes Claude over-apply the rule. If it's a rule that can't bend, turn it into a hook or a deny rule. If the line is getting lost in a long file, the file needs to be shorter." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- "Describe your architecture and file layout in CLAUDE.md": retired. "Claude reads the repo itself. Only write down what isn't in there." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- "Tell Claude to keep going, loop until done, don't be lazy": retired; such lines "are more likely to cause over-work than fix a stall." "think hard / be thorough" are ordinary prompt text; effort level is the real control. [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- "Delegate to a subagent for a better answer": retired. "Handing the same task to a subagent doesn't make the answer any better. A fresh reviewer does help, because it hasn't seen your reasoning." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- The API prompting guide says the same for tool and skill triggering: "Where you might have said 'CRITICAL: You MUST use this tool when...', you can use more normal prompting such as 'Use this tool when...' instead." Instructions like "If in doubt, use [tool]" cause overtriggering. [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

Prompt specificity, planning and workflow
- Specific prompts: instead of "fix the login bug", "users report login fails after the session times out. look at token refresh in src/auth/, write a failing test that reproduces it, then fix it". Instead of "add a calendar widget", "follow the pattern in HotDogWidget.php and build a calendar widget... no new libraries". [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Pointing at an existing house example ("follow the pattern in X") is the recommended way to get a convention followed. [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Claude "tends to read a request conservatively and build the smallest thing that satisfies it"; "be ambitious" with an explicit scope list is a phrase the docs say still helps. [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Spec first: ask Claude to interview you until it could write SPEC.md, then "start a fresh session to build from it, so the build begins with a clean context and a written definition of done." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Plan mode: "Claude reads files and proposes a plan but makes no edits until you approve" (Shift+Tab or `--permission-mode plan`). [Claude Code common workflows](https://code.claude.com/docs/en/common-workflows)
- The older Anthropic engineering post at anthropic.com/engineering/claude-code-best-practices (the source of the widely cited "explore, plan, code, commit" workflow) now 308-redirects to the docs page above, which no longer presents that four-step recipe by name; the current equivalent is spec/interview, plan mode, a check to run, and review. [redirect observed on fetch of anthropic.com/engineering/claude-code-best-practices](https://www.anthropic.com/engineering/claude-code-best-practices)

Verification and review
- "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually is done, 'looks done' is all it has to go on. In practice that makes you the test suite." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Ladder of strictness: ask in the prompt; `/goal` (a separate model checks a condition after every turn); a `Stop` hook that exits 2 until e.g. `pnpm tsc --noEmit` passes; a fresh-context reviewer (`/code-review`). "A line like 'Always typecheck before you finish' in this file works most of the time, not every time." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Ask for evidence: "'All tests pass' on its own tells you very little." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Reviewer prompts should say "skip style": "A reviewer that's asked to find problems will always find something. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Formatter as a `PostToolUse` hook on Edit|Write: "whether Claude remembers the rule no longer matters, because Claude isn't the one running it." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)

Context management and long sessions
- Steering: "Watch the first minute, press Esc the moment Claude drifts, and after two failed corrections run /clear and write a better prompt instead of a third." A third correction "mostly adds to a conversation that already contains two failed attempts for Claude to keep re-reading." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- `/clear` between unrelated tasks; `/compact` with a focus ("keep the API changes and the test commands"). Conversation-stated boundaries such as "don't push until I've reviewed" "can get lost when the conversation compacts, so anything that matters belongs in a deny rule." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Context rot: "the model's ability to accurately recall information from that context decreases" as context grows; context is a finite "attention budget". [Anthropic, Effective context engineering for AI agents, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- System prompts should sit at the "right altitude": between brittle hardcoded if-else logic and "vague, high-level guidance" that assumes shared context; start minimal and refine based on observed failures; use "a few diverse, canonical examples" rather than a laundry list of edge cases; keep lightweight references (file paths) and load data just in time; use structured note-taking (e.g., NOTES.md, to-do list) outside the window. [Anthropic, Effective context engineering, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Multi-window state: have the model keep tests in a structured file (tests.json), progress notes (progress.txt) and use git as the state log; "Claude's latest models are extremely effective at discovering state from the local filesystem", so starting fresh can beat compaction. [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

Subagents
- Subagents pay off for parallel independent work, keeping long output out of the main context, an unbiased reviewer, and restricted tool sets (a reviewer with only `tools: Read, Grep, Glob` cannot edit, "enforced by Claude Code rather than requested in a prompt"). Costs: tokens, and a fresh subagent "first has to gather context your conversation already had, so it can end up slower." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Prompting guide notes recent Opus models "have a strong tendency to use subagents and might spawn them in situations where a simpler, direct approach would suffice." [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

Skills
- Team procedures go in skills (`.claude/skills/<name>/SKILL.md`). Only name and description load every session; the body loads when relevant, so "A long release procedure sitting in a skill doesn't weigh on your unrelated bug fix the way it would in CLAUDE.md." Side-effect workflows get `disable-model-invocation: true` so only the user can start them. "The CLAUDE.md rule applies to skills too: only write down what Claude can't find on its own." [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Skill authoring: "Default assumption: Claude is already very smart. Only add context Claude doesn't already have." Ask "Does this paragraph justify its token cost?" [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "Set appropriate degrees of freedom": high freedom (text heuristics) when many approaches are valid; low freedom ("Run exactly this script... Do not modify the command") for fragile, sequence-critical operations ("narrow bridge with cliffs on both sides"). [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Keep SKILL.md body under 500 lines; progressive disclosure into reference files kept "one level deep" (nested references get partially read with `head -100`); table of contents for reference files over 100 lines. [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Descriptions: third person, say what it does and when to use it, include trigger terms; "Claude uses it to choose the right Skill from potentially 100+ available Skills." [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Feedback loops: "Run validator, fix errors, repeat. This pattern greatly improves output quality." Plan-validate-execute with a machine-checked intermediate file for batch or destructive changes. Prefer bundled scripts for deterministic operations ("more reliable than generated code"). [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- "Avoid offering too many options": provide a default with an escape hatch. Use consistent terminology. Avoid time-sensitive info. [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Evaluation-driven: "Create evaluations BEFORE writing extensive documentation": run without the skill, document failures, build three scenarios, baseline, "Write minimal instructions", iterate. Test with every model you will use (Haiku may need more detail, Opus may be over-explained to). [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Notably, the skill guide still suggests a refinement may use "stronger language such as 'MUST filter' instead of 'always filter'" when an agent misses a rule, which sits in mild tension with the Claude Code page's advice against emphasis. [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); contrast [Claude Code best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- Anthropic's guidance has shifted over 2025 to 2026 from "tune CLAUDE.md with emphasis" toward "short file of non-discoverable facts plus deterministic enforcement plus a check to run". For a skill teaching production quality code, the structural lesson is: put conventions an agent cannot infer (decisions, misleading legacy patterns, exact commands) in prose; put must-never rules in hooks/lint/CI; keep everything else out.
- The explicit warning that emphasis causes over-application matters for any skill that uses ALL CAPS rules: it can produce over-correction (e.g., refusing a legitimate exception).

### Gaps
- I could not re-read the original April 2025 Anthropic engineering post (it now redirects), so its exact wording of "explore, plan, code, commit" is not quoted here.
- Anthropic publishes no quantitative adherence numbers for the 200-line or 500-line thresholds; they are stated as guidance, not measured results.

## 2. What OpenAI Codex, AGENTS.md, Cursor, GitHub Copilot, Windsurf/Devin and Google Jules recommend

### Takeaway
All major vendors converge on the same shape: a short, accurate, layered markdown file (AGENTS.md is now the cross-tool standard under the Linux Foundation), path-scoped rules for subsystems, skills or on-demand rules for occasional procedures, linters and CI for formatting, and explicit "how to verify done" commands. Several vendors say to add rules only after observing a repeated mistake, and to avoid generic quality exhortations.

### Cited Findings

AGENTS.md standard
- "A simple, open format for guiding coding agents", "a README for agents"; no required fields. Suggested sections: project overview, build and test commands, code style guidelines, testing instructions, security considerations; plus commit/PR guidelines and deployment steps. [agents.md](https://agents.md/)
- Nesting: "Agents automatically read the nearest file in the directory tree, so the closest one takes precedence"; "explicit user chat prompts override everything." [agents.md](https://agents.md/)
- Stewardship and adoption: "AGENTS.md is now stewarded by the Agentic AI Foundation under the Linux Foundation"; "used by over 60k open-source projects"; OpenAI's main repo had 88 AGENTS.md files. Listed supporting tools include Codex, Jules, Cursor, Copilot coding agent, Gemini CLI, Windsurf, Devin, Aider, Zed, Warp, VS Code, JetBrains Junie, Amp, Factory and others. [agents.md](https://agents.md/)

OpenAI Codex
- Prompt contents: Goal, Context (files, docs, errors), Constraints (standards, conventions, safety) and "Done when". [Codex best practices](https://learn.chatgpt.com/docs/learn/best-practices) (no date shown on page)
- Plan first for complex or ambiguous tasks: Plan mode ("lets Codex gather context, ask clarifying questions, and build a stronger plan before implementation"), an interview, or a PLANS.md / execution-plan template for multi-step work. [Codex best practices](https://learn.chatgpt.com/docs/learn/best-practices)
- AGENTS.md: include repo layout, run instructions, build/test/lint commands, conventions, do-not rules, and how to verify done. "A short, accurate AGENTS.md is more useful than a long file full of vague rules." "Start with the basics, then add new rules only after you notice repeated mistakes." When Codex repeats a mistake, ask it for a retrospective and update the file. [Codex best practices](https://learn.chatgpt.com/docs/learn/best-practices)
- Listed common mistakes: putting durable rules in prompts instead of AGENTS.md or skills; not telling the agent how to run builds and tests; skipping planning on complex tasks; using one chat for a whole project. [Codex best practices](https://learn.chatgpt.com/docs/learn/best-practices)
- Skills: one job per skill, 2 to 3 concrete use cases, a description saying what and when; "if you keep reusing the same prompt or correcting the same workflow" it should become a skill. Team review standards go in a code_review.md referenced from AGENTS.md. [Codex best practices](https://learn.chatgpt.com/docs/learn/best-practices)
- Discovery: global `~/.codex/AGENTS.override.md` or `AGENTS.md`, then one file per directory from the project root down to cwd, concatenated root first; "Files closer to your current directory override earlier guidance because they appear later in the combined prompt." Combined size capped at `project_doc_max_bytes`, 32 KiB by default. For review rules, "reserve formatting and lint checks for CI." [Codex AGENTS.md docs](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

Cursor
- Rule types: Always Apply, Apply Intelligently (agent decides from description), Apply to Specific Files (glob), Apply Manually (@-mention). Project rules are `.mdc` files in `.cursor/rules` with `description`, `globs`, `alwaysApply` frontmatter. [Cursor rules docs](https://cursor.com/docs/context/rules)
- "Good rules are focused, actionable, and scoped." Keep each rule under 500 lines; give concrete examples or reference files; reference files rather than copying them so rules don't go stale. [Cursor rules docs](https://cursor.com/docs/context/rules)
- Avoid: pasting full style guides (use a linter instead, the agent already knows common conventions), documenting every command, rare edge-case instructions, duplicating code already in the codebase. [Cursor rules docs](https://cursor.com/docs/context/rules)
- Supports root and nested AGENTS.md; Team Rules > Project Rules > User Rules precedence; admins can make team rules required. [Cursor rules docs](https://cursor.com/docs/context/rules)

GitHub Copilot
- Files: `.github/copilot-instructions.md` (repo-wide), `.github/instructions/*.instructions.md` with `applyTo` globs and optional `excludeAgent`, AGENTS.md anywhere (nearest wins), or a root CLAUDE.md / GEMINI.md. [GitHub Docs, repository custom instructions](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)
- GitHub's own generation prompt: "Instructions must be no longer than 2 pages"; "Instructions must not be task specific"; include repo summary, validated bootstrap/build/test/run/lint commands with versions and known workarounds, project layout, CI checks, non-obvious dependencies; "Use language to indicate when something should always be done." [GitHub Docs, repository custom instructions](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)
- Code review reads only the first 4,000 characters of any instruction file (limit does not apply to Chat or the cloud agent); review uses the base branch's instructions. [GitHub Docs, code review (via search result)](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/request-a-code-review/use-code-review)
- Best practices for review instructions: "Shorter instruction files are more likely to be fully processed"; headings plus short imperative bullets; "Include code snippets showing both correct and incorrect patterns"; scope by path; "Begin with 10 to 20 specific instructions" and add rules one at a time, testing each on a real PR. What does not work: vague goals like "Be more accurate" or "Don't miss any issues" (noise), external links (cannot be followed, copy the standard in), changing comment format or merge blocking. [GitHub Docs, customize code review](https://docs.github.com/en/copilot/tutorials/customize-code-review)

Windsurf (now Devin Local / Devin Desktop, Cognition)
- The Windsurf docs URL now redirects to docs.devin.ai; legacy `.windsurf/rules/*.md`, `.windsurf/global_rules.md` and `.windsurfrules` are imported by default; new locations are `.devin/rules/*.md` and `.devin/global_rules.md`; AGENTS.md, AGENTS.local.md and AGENT.md are read as always-on rules in each directory from workspace root to cwd. [Devin Local rules docs](https://docs.devin.ai/desktop/cascade/memories)
- Activation modes: `always_on`, `glob`, `model_decision`, `manual`. "Rules are in the context of every session, so they cost tokens on every message." Use a skill for occasional needs and a rule to point at the right skill; format as bullets, numbered lists and headers; leave out generic rules such as "write good code". [Devin Local rules docs](https://docs.devin.ai/desktop/cascade/memories)

Google Jules
- Jules runs each task in a short-lived VM; for simple setups it infers the environment and "can refer to agents.md or your readme.md file for hints"; complex setups should use a lightweight setup script, snapshotted after a successful run. [Jules environment docs](https://jules.google/docs/environment/)
- A third-party guide warns that install commands written in AGENTS.md are treated as guidance rather than executed; the setup script is what actually installs. [thepromptshelf.dev (secondary)](https://thepromptshelf.dev/blog/google-jules-agents-md-setup-guide-2026)

### Inferences
- The consensus "contents list" across vendors is: exact commands to build/test/lint and how to verify done; non-obvious conventions and decisions; do-not rules for footguns; layered scoping. None recommends architecture overviews as a priority (Anthropic explicitly retired it), which matches the empirical findings below.
- Size budgets differ per tool (Claude: under 200 lines per file; Codex: 32 KiB combined cap; Cursor: under 500 lines per rule; Copilot review: first 4,000 chars only; skills: under 500 lines). A cross-tool file should fit the tightest of these (the 4,000 character Copilot review cap) for anything review-critical, placed at the top.

### Gaps
- OpenAI's Codex prompting guide and execution-plans (PLANS.md) cookbook pages were not fetched; only the best-practices summary of them.
- I did not find a current official Windsurf character-limit figure (older Windsurf docs had per-file limits; the Devin page does not state one).

## 3. Evidence on what makes agents follow instructions (length, specificity, phrasing, examples, ordering, rules as operations, decay) and studies of AGENTS.md / CLAUDE.md files

### Takeaway
Controlled studies (2026) find that repository context files do not measurably raise task success, LLM-generated ones slightly lower it and raise cost by about 20%, while developer-written ones are neutral to slightly positive. But agents do follow specific operational instructions reliably (named tools get used about 160 times more often), and files can cut runtime and wasted test runs. Separately, instruction-following degrades with instruction count, context length and conversation turns, which supports short, specific, operational files and fresh sessions.

### Cited Findings

Controlled studies of context files
- Gloaguen et al., "Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?" (ETH Zurich / LogicStar; arXiv 2602.11988, v1 2026-02-12, v3 2026-09-29). Agents: Claude Code with Sonnet-4.5, Codex with GPT-5.2 and GPT-5.1 mini, Qwen Code with Qwen3-30b-coder. Benchmarks: SWE-bench Lite (300 tasks) with LLM-generated files, and a new CTXbench of 138 instances from 12 repos with developer-committed files. [arXiv HTML](https://arxiv.org/html/2602.11988)
  - LLM-generated files: about -0.5% success on SWE-bench and -2% on CTXbench (not significant, p = 0.87, 0.37); cost up about 20% and 23%; about 2.45 and 3.92 extra steps (significant). [arXiv HTML](https://arxiv.org/html/2602.11988)
  - Developer-written files: about +2.4% on CTXbench (p = 0.21, not significant), about 3.34 extra steps, cost up to 19%. Developer vs LLM-generated difference significant (p = 0.038). [arXiv HTML](https://arxiv.org/html/2602.11988)
  - Instructions ARE followed: when `uv` was mentioned it was used 1.6 times per instance vs under 0.01 when not; repo-specific tools 2.5 vs under 0.05. Context files increased test runs, searches, file reads and writes; GPT-5.2 reasoning tokens rose 22% (SWE-bench) and 14% (CTXbench). [arXiv HTML](https://arxiv.org/html/2602.11988)
  - Overviews do not help: Sonnet-4.5's generated files contained overviews 100% of the time but did not reduce steps to reach the files the PR modified. [arXiv HTML](https://arxiv.org/html/2602.11988)
  - When other docs were removed from the repo, LLM-generated files improved performance by about 2.7%, i.e., they help mainly when they are the only documentation. [arXiv HTML](https://arxiv.org/html/2602.11988)
  - Authors' advice: omit LLM-generated context files for now; keep human-written files to "minimal requirements" not already in the README, such as specific conventions or non-functional requirements; "context files are useful for specifying non-standard coding practices"; evaluate before deploying. [arXiv abstract](https://arxiv.org/abs/2602.11988)
- Lulla et al., "On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents" (arXiv 2601.20404, v1 2026-01-28, v2 2026-03-30): 10 repos, 124 PRs, Codex-family agents with vs without AGENTS.md: median runtime down 28.64%, output tokens down 16.58%, task completion "comparable". [arXiv abstract](https://arxiv.org/abs/2601.20404)
- Khatri, "Do Context Files Help Coding Agents? A Two-Agent Ablation Study on Real Repositories" (arXiv 2607.27250, 2026-07-28, single author): Claude Code (claude-sonnet-4-6) and Codex CLI (gpt-5.5), 3 Python repos, 291 runs. Pass rates: Claude 53.3% none / 55.6% always-on / 55.6% selective (p = 1.000); Codex 58.8% / 56.9% / 52.9% (p = 0.66). Near-miss failures were about "implementation skill: feature design, pattern choice, and exact wiring", not missing facts; in a 36-cell probe the real AGENTS.md "never turned a near-miss into a pass". On one repo Claude's full-suite test runs fell from 3.67 to 2.44 (always-on) to 1.67 (selective). Authors suggest effort on generic context documents may pay off less than "task decomposition, tooling, or example-driven prompting". Underpowered: minimum detectable effect over 30 percentage points; 120 to 200 tasks needed to detect 10pp. [arXiv HTML](https://arxiv.org/html/2607.27250v1)

Observational studies of files in the wild
- Chatlatanagulchai et al., "Agent READMEs: An Empirical Study of Context Files for Agentic Coding" (arXiv 2511.12884, v1 2025-11-17, v2 2026-08-09): 2,303 files from 1,925 repos (CLAUDE.md, AGENTS.md, copilot-instructions.md). Content: testing procedures 75.9%, implementation details 70.8%, architecture 68.1%; security only 14.8%, performance 14.5%. Files "evolve like configuration code through frequent, small additions" and are hard to read; developers use them "to make agents functional" with "few guardrails" for secure or performant code. [arXiv abstract](https://arxiv.org/abs/2511.12884)
- Jiang and Nam, "Beyond the Prompt: An Empirical Study of Cursor Rules" (arXiv 2512.18925, MSR '26, v3 2026-03-04): 401 repos, 1,876 .mdc files. Share of repos covering each theme: Guideline 89%, Project 85%, Convention 84% (code style 65%, language/framework 64%, structure 59%), LLM Directive 50%, Example 50%. 28.70% of rule lines are exact duplicates across repos (copied from templates like awesome-cursor-rules), LLM Directive lines most duplicated. Authors note rule efficacy "is untested" and rules reflect developer intuition. [arXiv HTML](https://arxiv.org/html/2512.18925)
- Galster et al., "Harness Engineering for Agentic AI Coding Tools: An Exploratory Study" (arXiv 2602.14690, AIware 2026; v5 2026-06-30): 2,853 repos, eight configuration mechanisms across Claude Code, Copilot, Cursor, Gemini, Codex. Context files dominate and "are often the sole mechanism"; AGENTS.md is emerging as the cross-tool standard; skills and subagents are rare, and skills mostly hold static instructions rather than scripts. [arXiv abstract](https://arxiv.org/abs/2602.14690)

Instruction count, context length and turn decay
- IFScale, "How Many Instructions Can LLMs Follow at Once?" (Distyl AI, arXiv 2507.11538, July 2025, NeurIPS 2025): 20 models, up to 500 simultaneous keyword-inclusion instructions; best frontier models reach only about 68% accuracy at 500; shows a bias toward earlier instructions and three degradation patterns tied to model size and reasoning. [arXiv](https://arxiv.org/abs/2507.11538); [aitopics summary](https://aitopics.org/doc/arxivorg:08469166)
- Chroma, "Context Rot" (Hong, Troynikov, Huber, 2025-07-14): 18 LLMs including GPT-4.1, Claude 4, Gemini 2.5, Qwen3; performance becomes increasingly unreliable as input length grows even on trivial tasks, and worse when distractors are semantically close to the target. [Chroma research](https://research.trychroma.com/context-rot)
- Laban et al., "LLMs Get Lost In Multi-Turn Conversation" (arXiv 2505.06120, May 2025; ICLR 2026): average 39% drop from single-turn to multi-turn underspecified conversations across six generation tasks; mostly an unreliability increase (about 112%) rather than aptitude loss (about 16%); models "make assumptions in early turns and prematurely attempt to generate final solutions, on which they overly rely." Recaps and lower temperature did not fix it (per summaries). [arXiv](https://arxiv.org/pdf/2505.06120)
- These support Anthropic's "after two failed corrections, /clear and write a better prompt" and Codex's "one chat per coherent unit of work" advice. [Claude Code best practices](https://code.claude.com/docs/en/best-practices); [Codex best practices](https://learn.chatgpt.com/docs/learn/best-practices)

Phrasing: positive vs negative, emphasis, reasons, examples
- Anthropic: "Tell Claude what to do instead of what not to do" (e.g., instead of "Do not use markdown", "Your response should be composed of smoothly flowing prose paragraphs"). Matching the prompt's own style to the desired output also steers output. [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Anthropic: give the reason: "Providing context or motivation behind your instructions, such as explaining to Claude why such behavior is important... help it deliver more targeted responses" (example: "NEVER use ellipses" is the less effective form). [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Anthropic: "Examples are one of the most reliable ways to steer Claude's output format, tone, and structure"; make them relevant, diverse and wrapped in `<example>` tags; 3 to 5 examples. [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Anthropic: put long documents at the top, instructions and query after them. [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Anthropic documents an overengineering tendency in recent Opus models ("creating extra files, adding unnecessary abstractions, or building in flexibility that wasn't requested") and offers a sample instruction covering scope, documentation, defensive coding ("Only validate at system boundaries") and abstractions ("Don't design for hypothetical future requirements"). [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- "Semantic Gravity Wells: Why Negative Constraints Backfire" (arXiv 2601.08070, 2026): on Qwen2.5-7B-Instruct, negative instructions still reduce the forbidden word's probability but about 4.4 times less in failing cases; authors do not claim universality. [arXiv](https://arxiv.org/html/2601.08070v1)
- Older evidence: models performed worse on negated instructions across nine NLP benchmarks, and the gap widened with scale (NeurIPS 2022 workshop paper, "Can Large Language Models Truly Follow your Instructions?"). [NeurIPS 2022](https://neurips.cc/virtual/2022/65648)
- GitHub: show both correct and incorrect code ("avoid" vs "prefer") pairs; vague quality goals add noise. [GitHub Docs, customize code review](https://docs.github.com/en/copilot/tutorials/customize-code-review)

Rules as operations (practitioners)
- Mitchell Hashimoto (2026-02-05): "Each line in that file [AGENTS.md] is based on a bad agent behavior, and it almost completely resolved them all." He calls building tooling so "the agent never makes that mistake again" "harness engineering": scripts to take screenshots, run filtered tests, etc., "usually paired with an AGENTS.md change to let it know about this existing." "If you give an agent a way to verify its work, it more often than not fixes its own mistakes and prevents regressions." Split vague work into separate planning and execution sessions. [Mitchell Hashimoto, My AI Adoption Journey](https://mitchellh.com/writing/my-ai-adoption-journey)
- Armin Ronacher (2025-06-12): put critical tools in a Makefile; make them idempotent, fast ("Crashes are tolerable; hangs are problematic"), and loud on misuse ("Tools must clearly inform agents of misuse or errors"); log to files so the agent can read them (a CLAUDE.md line tells the agent emails are logged). Agents do best with simple code: "the dumbest possible thing that will work", descriptive long function names over classes, no clever hacks; hiding permission checks in another file "will almost guarantee" the agent omits them on new routes; agents may keep following outdated patterns after the reason is gone. [Armin Ronacher, Agentic Coding Recommendations](https://lucumr.pocoo.org/2025/6/12/agentic-coding/)

### Inferences
- The strongest evidence-backed lever is operational, not descriptive: naming a specific command or tool reliably changes behaviour (Gloaguen trace data), whereas overviews and generic advice do not change outcomes and cost tokens. A production-quality skill should therefore phrase conventions as concrete operations ("run X", "use helper Y in path Z", "copy the pattern in file F") with a check that fails when violated.
- Failures that remain with good context files are implementation-skill failures (design, pattern choice, wiring), so pointing at a concrete house example and requiring a verification loop is likely to help more than more prose. This is an inference from Khatri (small, single-author) and Anthropic/Hashimoto guidance, not a measured result.
- No study isolates the effect of individual phrasing choices (positive vs negative, with vs without reasons, emphasis) on coding agents specifically; vendor guidance and small mechanistic studies are the evidence base.
- Instruction-count and context-length decay (IFScale, Context Rot, Lost in multi-turn) suggest: few instructions, front-loaded critical rules (bias toward earlier instructions), path-scoped loading, and fresh sessions over long correction chains.

### Gaps
- No controlled study found that measures CLAUDE.md specifically (as opposed to AGENTS.md) on Claude Code task success with Claude 5.x-era models.
- No controlled study found on skills (SKILL.md) effectiveness for coding quality; Galster et al. only measure prevalence.
- No study found that measures code quality (maintainability, convention adherence) rather than test pass rate as the outcome of context files; all three controlled studies use pass/fail or efficiency.
- The "ratio of helpful to harmful instructions is unfavorable for verbose files" claim surfaced in a search snippet but could not be traced to a primary source.

## 4. How to capture conventions so an agent can follow them (style guides, lint configs, examples, decision records)

### Takeaway
Vendors agree: do not paste style guides into instruction files; encode mechanical conventions in linters, formatters and CI (and run them via hooks), point the agent at a canonical example file for the house pattern, and write down only decisions and gotchas that are not visible in the code (including "this legacy pattern is everywhere but do not copy it"). Decisions belong in the repo as text the agent can find, and project-specific procedures belong in skills.

### Cited Findings
- Cursor: do not paste full style guides; "use a linter instead", since Agent already knows common conventions; reference files instead of copying them; give concrete examples or reference files. [Cursor rules docs](https://cursor.com/docs/context/rules)
- Codex: "reserve formatting and lint checks for CI" when writing review rules; define "good" in the prompt or AGENTS.md including test suites and lint, format or type checks. [Codex AGENTS.md docs](https://learn.chatgpt.com/docs/agent-configuration/agents-md); [Codex best practices](https://learn.chatgpt.com/docs/learn/best-practices)
- Claude Code: formatting via a `PostToolUse` Prettier hook; protected paths via `PreToolUse` hook; the house pattern via "follow the pattern in HotDogWidget.php"; misleading legacy code stated explicitly ("src/legacy/ is still live but don't copy its patterns into new code"); team decisions stated ("Use the error helpers in src/lib/errors.ts, never throw raw strings"). [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Claude Code: decisions "made in a meeting" and processes in "one person's head" are exactly what the agent cannot discover and therefore what to write down. [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Claude Code docs observe Claude "examines your existing test files to match the style, frameworks, and assertion patterns already in use", i.e., existing code is itself the primary convention source. [Claude Code common workflows](https://code.claude.com/docs/en/common-workflows)
- GitHub: include correct and incorrect code pairs in instructions; copy standards into the file instead of linking to external resources (Copilot cannot follow links). [GitHub Docs, customize code review](https://docs.github.com/en/copilot/tutorials/customize-code-review)
- Factory (Alvin Sng, 2025-09-05), "Using Linters to Direct Agents": linters should encode architecture, boundary and style standards so agents get automatic feedback and self-correct; the same rules run on save, pre-commit, CI, PR bots and in the agent toolchain; example rule bans relative imports across package boundaries in favour of path aliases; also file-organization rules. (Seen via search summary, not fetched in full.) [Factory blog](https://www.factory.ai/using-linters-to-direct-agents)
- Hashimoto: convert each observed mistake into either an AGENTS.md line or a programmed tool/check the agent can run. [Mitchell Hashimoto](https://mitchellh.com/writing/my-ai-adoption-journey)
- Ronacher: keep critical tools discoverable in a Makefile and keep conventions local and explicit (permission checks next to the route rather than in config) because agents miss indirection. [Armin Ronacher](https://lucumr.pocoo.org/2025/6/12/agentic-coding/)
- Skill authoring: prefer bundled validation scripts over asking the model to generate checks; use a style-guide file plus an explicit review checklist loop when no script is possible ("The 'validator' is STYLE_GUIDE.md"). [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Gloaguen et al. recommend context files hold non-standard practices and non-functional requirements, the categories that Chatlatanagulchai et al. found are rarely written down (security 14.8%, performance 14.5%). [arXiv 2602.11988](https://arxiv.org/abs/2602.11988); [arXiv 2511.12884](https://arxiv.org/abs/2511.12884)

### Inferences
- A practical capture hierarchy emerging from the sources: (1) lint/format/type rules and CI for anything mechanically checkable; (2) hooks or deny rules for zero-exception constraints; (3) a canonical example file per pattern, named in the instruction file; (4) a short instruction file with commands, non-obvious decisions, "do not copy" warnings and non-functional requirements; (5) skills for procedures used occasionally. Prose description of style is the last resort.
- Because the field data shows security and performance are rarely specified, a skill aiming at production quality should explicitly add those non-functional requirements, ideally backed by checks.

### Gaps
- No vendor document found that discusses Architecture Decision Records (ADRs) specifically as agent input; the closest is Anthropic's "decisions that aren't in the repo" guidance.
- No empirical study found comparing lint-enforced conventions vs prose-stated conventions for agent adherence; the case for linters rests on vendor guidance and practitioner reports.
